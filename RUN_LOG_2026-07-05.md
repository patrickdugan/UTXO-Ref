## Update — 2026-07-06, refund CET cadence changed to 24 hours

Per user request, the refund CET's CSV delay default was changed from a
2-block test value to **576 blocks (24 hours at Litecoin's ~2.5 min target
block time: 86,400s / 150s = 576)**. `--csv <n>` still overrides for fast
testing.

Waiting inline for 576 confirmations is impractical in a single script
invocation, so `tradelayer_dlc_refund_cet_demo.js` was restructured into
two phases:

1. **Fund + pre-sign** (`--broadcast`, unchanged flag): builds the refund
   tx, broadcasts only the funding tx, and saves the fully pre-signed
   refund spend hex to `artifacts/live/dlc_refund_cet_latest.json`
   (`refundSpendHex` field). Returns immediately — no polling.
2. **Settle** (new `--settle <fundingTxid>` flag): checks the funding tx's
   live confirmation count via RPC; if `>= csvDelay`, broadcasts the saved
   `refundSpendHex`; otherwise reports confirmations so far and estimated
   remaining wait.

Both phases were verified against the live LTCTEST node:

- **Dry run** (`--csv` default, no `--broadcast`): printed `csv delay: 576
  blocks (~24.0 hours...)` and a full pre-signed-but-unbroadcast summary —
  confirms the arithmetic and script construction are unaffected by the
  larger CSV value.
- **Real broadcast**: funding txid
  `fb2c69028faf114164dc552fc83b7a4c31b198b097f4beeb2479eff1eb914314`
  broadcast successfully; driver printed the exact `--settle` command to
  run once matured instead of blocking.
- **Settle check (immediately after, 0 confirmations)**: correctly reported
  `0/576 confirmations` and `NOT YET MATURE — 576 more confirmation(s)
  needed (~1440 min...)` without attempting to broadcast the refund early.

**This production-cadence run's funding tx (`fb2c6902…1eb914314`) is still
pending as of this entry** — its refund spend will not be broadcastable
until ~24 hours after the funding tx confirms. To complete it: re-run

## Node process terminated before reaching RPC-ready (first attempt, superseded above)

After ~24+ minutes of observed (slow but real) progress, the background
`litecoind` process was killed by the harness — the task notification
reported status `killed` with no corresponding graceful-shutdown entry
(`Shutdown: in progress...` / `Shutdown: done`) in `debug.log`, meaning it
was terminated abruptly rather than stopped cleanly. This appears to be an
environment limit on how long a background task can run in this session
rather than anything related to the node's own health — the last resource
snapshot before termination showed CPU and memory still climbing
normally (Section "Node startup" above).

**Practical implication:** a `litecoind` cold-start from a ~6-month-old
datadir does not reliably finish within one interactive session's
background-task budget here. Options for completing Tasks 1 and 4:

1. Start the node from a separate, persistent terminal outside this
   session (e.g. via the `!` prefix, or a normal shell), let it fully sync
   to RPC-ready, then hand off to this session to run the two demo
   commands in the section above.
2. Re-attempt the background start in a fresh session immediately after
   this one, on the theory that the block index is now partially warmed
   in the OS disk cache from this attempt and may load faster the second
   time (not verified — the abrupt kill means the index write state is
   unconfirmed; litecoind's own crash-recovery/reindex-on-next-start
   behavior would apply as normal).

No further automatic retry was attempted in this pass.
